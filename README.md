## 功能简介

脱离电脑环境采集杰理音箱 / 耳机的串口音频数据，流程只有三步：

1. **采集**：设备通过串口（UART）发出音频数据包，小板实时接收、校验 CRC、按通道解复用，直接写成 `JL_DEBUG/rec_NNN/0.raw`、`1.raw`、`2.raw`……每个 `.raw` 就是一个声道
2. **状态提示**：OLED 或串口打印反馈格式（V1/V2）、SD 状态、波特率、通道数、单通道长度、已采集数据量、丢包数
3. **分析**：把卡插到电脑上，用 Adobe Audition 按数据实际的 **位宽、采样率、声道数** 打开 `.raw` 看波形

> 分通道在小板上就做完了，**正常情况下不再需要电脑端解析脚本**。

## 按键说明

**默认配置：** 通道数 `3`、单通道长度 `512` 字节、波特率 `2000000`

### 操作流程

`PP` 键循环切换档位，`NEXT` / `PREV` 加减当前档位的值：

```
档位 0（不设置） → 1（ch） → 2（len） → 3（baud） → 回到 0
        每按一次 PP 前进一档
```

回到档位 0 时**自动重启接收任务**，新参数立刻生效，**不用重启小板**。

### 长按连调

`NEXT` / `PREV` 支持长按：按住不放会连续加减。`len` 一步只加 4，从 512 调到别的值靠短按要按上百下，长按几秒就到。

调到上限会停住不再变，串口同时打印当前上限：

```
pcm_rx_single_size : 0680 (max 680)
pcm channel : 03 (max 3)
```

### 可调范围

**约束只有一条不等式：**

```
len × ch ≤ 8188        另加 ch ≤ 8

8188 = UART_FRAME_LIMIT - UART_FRAME_CRC_LEN = 16384 / 2 - 4
```

串口收帧长度是 `len × ch + 4`，DMA 环形缓冲至少要装得下两帧才不会在任务搬运期间被覆盖，所以帧长上限取缓冲的一半。

固件不会同时改两个值，调哪个就用另一个反算上限，所以下面两张表是**同一条不等式的两个方向**，不是两组独立规则：

**调 `len` 时**（上限 = `8188 / 当前 ch`，向下取整到 4 的倍数）

| 当前 ch | 1    | 2    | 3    | 4    | 5    | 6    | 7    | 8    |
| ------- | ---- | ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| len 上限 | 8188 | 4092 | 2728 | 2044 | 1636 | 1364 | 1168 | 1020 |

**调 `ch` 时**（上限 = `8188 / 当前 len`，再压到 8 以内）

| 当前 len | 512 | 1024 | 1364 | 2048 | 2728 | 4096 | 8188 |
| -------- | --- | ---- | ---- | ---- | ---- | ---- | ---- |
| ch 上限  | 8   | 7    | 6    | 3    | 3    | 1    | 1    |

> 两张表互相印证：第一张查到 `ch=5 → len ≤ 1636`，第二张查 `len=1364 → ch ≤ 6`，代回去 `5 × 1636 = 8180 ≤ 8188`、`6 × 1364 = 8184 ≤ 8188`，都贴着上限。**不要横向读一行去凑 `ch` 和 `len`**——每张表的行是独立的取值，不是配对关系。
>
> `len=512 → ch 上限 8` 是被 `ch ≤ 8` 压出来的，不等式本身允许 15。

其余限制：

- `len` 步长 4，下限 4；`ch` 步长 1，下限 1
- 波特率 1M～9M，步长 1M
- 若 syscfg 里存的是越界的旧值，按一下 `NEXT` 会先把它拉回上限，而不是继续加
- 屏上 / 打印里的 `(max N)` 就是按当前另一个值算出来的实时上限

> 要放宽上限，得同时改 `audio_uart_receive.c` 的 `uart_dma_buf_size` 和 `idle_app_msg_handler.c` 的 `UART_DMA_BUF_SIZE`，两个值必须一致（源码注释里有说明）。

## SD 卡上的文件结构

每次开始接收数据都新建一个子目录：

```
storage/sd0/C/JL_DEBUG/
├── rec_000/
│   ├── 0.raw        ← 通道 0
│   ├── 1.raw        ← 通道 1
│   └── 2.raw        ← 通道 2
├── rec_001/
└── rec_014/         ← 序号最大的是最新一次
```

- 目录名 `rec_NNN`，序号从 000 递增，上限 1000
- 文件名就是通道号，`.raw` 是裸数据，没有任何文件头
- **全是 0 字节的目录会被复用**，不会白占序号（建好文件后要攒满一个块才落盘，这期间断电或拔卡就会留下空文件）
- V2 的通道号来自数据包包头，不保证从 0 开始，所以目录里可能只有 `1.raw`、`2.raw`

## V1 与 V2 格式

两种格式共用同一个**串口帧**外壳，区别只在帧里的载荷怎么组织。

### 串口帧（两种格式共用）

接收端按固定长度切帧，帧长由屏上的 `ch`、`len` 算出：

```
帧长 = ch × len + 4

+---------------------------+--------+--------+
|  载荷  ch × len 字节      | CRC16  | 填充   |
|                           | 2 字节 | 2 字节 |
+---------------------------+--------+--------+
```

- CRC 是 **CRC-16/XMODEM**（poly 0x1021，init 0x0000，无反转、无末异或），**只覆盖载荷**，不含自己和填充
- CRC 按小端存在字节偏移 `ch × len` 处；最后 2 字节填充内容不校验
- 载荷长度必须是偶数（接收端按半字取 CRC）

接收端**只用 `ch × len` 的乘积**算帧长和 CRC 范围，从不单独看 `ch` 或 `len`：

```c
hdl->uart_frame_size = hdl->pcm_rx_single_size * hdl->pcm_channel + 4;
crc16 = CRC16(hdl->uart_tmp_buf, hdl->uart_frame_size - 4);
if (crc16 == hdl->uart_tmp_buf[(hdl->uart_frame_size - 4) / 2]) { ... }
```

所以**唯一的硬要求是帧长相等**：

> **`ch × len` = 发送端每帧的载荷字节数**

| 发送端每帧 | 屏上要配 `ch × len` | 可选拆法 |
| ---------- | ------------------- | -------- |
| 512 + 4    | 512                 | 1×512、2×256、4×128、8×64 |
| 1024 + 4   | 1024                | 1×1024、2×512、4×256、8×128 |
| 1536 + 4   | 1536                | 3×512、2×768、6×256 |
| n × 512 + 4 | n × 512            | 任意乘积相等的组合 |

配错的现象是刷屏的 CRC 错，很容易误判成硬件问题：

```
uart crc err
uart crc err
uart recv read err, 1048 1540
```

`uart recv read err` 后面两个数是"实收 / 期望"，拿期望值除以发送端帧长就知道差多少。

### 自动嗅探

开机后由数据内容自动判定 V1 / V2，结果显示在屏幕左上角，同时打印：

```
[raw] sniff: V1 assumed, ch 3 len 512
[raw] sniff: V2 run 4 at offset 12
```

嗅探只看字节流内容（V2 包头的 magic、len、CRC），**完全不参考屏上的 `ch` / `len`**。但它工作在串口帧校验的下游——帧长配错时一个字节都进不来，接收端只会补零，于是必然误判成 V1。**看到该收 V2 却显示 V1，先查 `ch × len`，不要怀疑嗅探。**

### V1（定长交织）

载荷是定长交织块，没有任何自描述信息：

```
+---------+---------+-----+-----------+
|  ch0    |  ch1    | ... |  chN-1    |    每段 len 字节
+---------+---------+-----+-----------+
```

通道归属完全靠字节在块里的位置，所以 **V1 的 `ch` 和 `len` 必须和发送端逐个一致**，不只是乘积相等。错一个字节，后面所有通道整体错位。

### V2（带包头的包流）

载荷是**无边界的包字节流**，串口帧只负责搬运：

```
[包头 20B][data][包头 20B][data][包头 20B][data...
                                 ^^^^^^^^^^^^^^^^ 可以跨帧
```

- 一帧里可以有多个包，也可以只有某个包的碎片；**包允许跨帧**，接收端用 `parse_buf` 拼接
- 攒不满一帧的部分发送端会留着等下一次，所以包边界和帧边界无关
- 每包 `data` 长度可以不同，上限 `RAW_V2_MAX_DATA`（10240）

**通道数和屏上的 `ch` 没有关系。** 通道号取自包头的 `ch` 字段，上界是编译期常量 `RAW_MAX_CH`（8），文件用到才建：

```c
if (h->ch >= RAW_MAX_CH) { rw->err_cnt++; return; }   /*不是 v1_ch*/
c = raw_ch_get((u8)h->ch);                            /*首次用到才 fopen*/
```

| 情况 | 结果 |
| ---- | ---- |
| 屏上 `ch=1`，流里跑 4 个通道 | 照样生成 `0.raw`~`3.raw`，一个不漏 |
| 屏上 `ch=8`，流里只有 2 个通道 | 只生成 `0.raw`、`1.raw`，不会建空文件 |
| 包头 `ch ≥ 8` | 丢包并累加 `err_cnt` |

所以 V2 下屏上的 `ch` 只剩两个作用：

| 作用 | 影响 |
| ---- | ---- |
| 参与算帧长 `ch × len + 4` | **致命**，配错一个字节都收不到 |
| 当 `raw_ch_stagger_th()` 的除数，排各通道落盘相位 | 只影响写卡毛刺分布，不影响数据正确性 |

**建议把 `ch` 填成实际通道数**，`len` 用 `载荷长度 / ch`，这样两个作用同时满足（比如发送端 1024+4、实际 2 通道 → 配 `ch=2 / len=512`）。

### V2 包头格式

20 字节，全部小端：

| 偏移 | 长度 | 字段 | 说明 |
| ---- | ---- | ---- | ---- |
| 0  | 2 | `magic`     | 固定 `0x2B5A` |
| 2  | 2 | `ch`        | 通道号，接收端据此归档，须 < 8 |
| 4  | 2 | `seqn`      | 该通道的包序号，接收端不校验 |
| 6  | 2 | `crc`       | **CRC-16/XMODEM(data, len)**，只覆盖 data，不含包头 |
| 8  | 2 | `len`       | data 字节数，每包可不同，须在 1…10240 |
| 10 | 2 | `rsvd`      | 发送端的编译器对齐空洞，**内容是未初始化的栈垃圾，不可读取** |
| 12 | 4 | `timestamp` | 发送时刻的 jiffies，接收端不校验 |
| 16 | 4 | `total_len` | 该通道累计字节数，**含本包** |

`total_len` 是丢包补偿的依据：接收端算 `expect = total_len - len`，若 `expect` 大于该通道已写入的字节数，说明中途丢了包，会**补等量的零**再写本包，保证各通道时间轴对齐，否则做延时 / 回声分析时通道之间会整体错位。补零同时累加 `err_cnt`。

### 移植发送端的检查清单

改发送端帧长（例如 512 → 1024）时，这几处要一起动：

- [ ] 攒够 **1024** 字节才组帧发送（原来是 512）
- [ ] CRC16 存到**字节偏移 1024**，即 `u16 *` 缓冲的下标 `[512]`（原来是 `[256]`）
- [ ] 帧总长 `uartSendData(buf, 1028)`（原来是 516）
- [ ] CRC 算法保持 XMODEM，**只覆盖那 1024 字节载荷**
- [ ] 末尾留 2 字节填充，内容不限
- [ ] 接收端屏上改成 `ch × len = 1024`

接收端在 `len × ch ≤ 8188` 范围内不需要改代码（缓冲、DMA 环形区都是按帧长自动分配的）。

## 打印说明（无显示屏时使用）

打印波特率 `2000000`。

### 正常流程

```
=================================== pcm channel : 3
=================================== pcm_rx_single_size : 512
=================================== uart_baud_rate : 2000000
[raw] use new dir storage/sd0/C/JL_DEBUG/rec_014
[raw] sniff: V1 assumed, ch 3 len 512
[raw] create storage/sd0/C/JL_DEBUG/rec_014/0.raw (343ms)
[raw] create storage/sd0/C/JL_DEBUG/rec_014/1.raw (8ms)
[raw] create storage/sd0/C/JL_DEBUG/rec_014/2.raw (9ms)
```

之后进入稳定收发，交替打印 `R`（收到一帧）和 `W`（搬一批数据去写卡）。

### 写卡耗时诊断

单次写盘超过 30ms 才打印，正常不会刷屏：

```
[raw] slow w ch2 82ms len 16384 tot 102911
        │        │      │           └ 该通道累计字节数
        │        │      └ 本次写入字节数
        │        └ 本次 fwrite 耗时
        └ 通道号
```

正常范围 30～85ms。**偶发几百毫秒到 1 秒**的是 TF 卡内部的擦除 / 垃圾回收，软件规避不了；上游缓冲已经按 1.5 秒余量设计，这种停顿不会丢包。如果频繁出现且伴随 `sd cbuf full`，换一张写入延迟更稳定的卡。

### 异常打印

| 打印                                      | 含义                                                                 |
| ----------------------------------------- | -------------------------------------------------------------------- |
| `[error] sd cbuf full, cbuf data len N` | 上游缓冲被打满，**这一帧丢了**，`lost` 会加一                |
| `uart crc err`                          | 帧校验失败。刷屏出现基本都是`ch`/`len` 配错，先核对帧长          |
| `uart recv read err, A B`               | 收到 A 字节但期望 B 字节，同上                                       |
| `[raw] sd write err N/M`                | 写盘失败，通常是卡被拔了                                             |
| `timer_no_response: dev_mg, ...`        | 写盘卡住期间定时器误点，是停顿的**症状**不是故障，数据不受影响 |

## FAQ

**Q1：按键改了参数要重启小板吗？**
不用。`PP` 键转回档位 0（光标全部消失）时会自动重启接收任务，参数立刻生效。

**Q2：屏幕左上角一直是 `--`？**
格式还没嗅探出来，说明**一帧有效数据都没收到**。先看串口是不是在刷 `uart crc err`，那就是 `ch`/`len` 配错了帧长。

**Q3：测 V2 收不到数据，`ch`/`len` 该配多少？**
只有一个要求：**`ch × len` 等于发送端每帧的载荷字节数**（帧长减 4）。发送端 `512+4` 就配乘积 512，`1024+4` 就配 1024；怎么拆不影响解析，V2 的真实通道号在包头里。建议 `ch` 填实际通道数、`len` 填 `载荷长度 / ch`。详见[V2（带包头的包流）](#v2带包头的包流)。

**Q4：`lost` 不是 0 怎么办？**
写卡过程有丢包。看串口是 `sd cbuf full`（卡太慢，换卡或降波特率）还是 `uart crc err`（帧长配错）。换卡后 `lost` 会自动归零。

**Q5：`sd:off` 是什么意思？**
SD 卡没正常识别。检查是否插好、换张卡试。在线插拔是支持的，重新插入会自动新建 `rec_NNN` 目录继续录。

**Q6：`.raw` 在 Audition 里打开是噪声？**
按数据实际的**位宽、采样率、声道数**打开。`.raw` 没有文件头，参数不对必然是噪声。注意每个 `.raw` 是**单声道**。

**Q7：哪个是最新的数据？**
`JL_DEBUG` 下序号最大的 `rec_NNN` 目录。

**Q8：串口一直刷 `timer_no_response: dev_mg`？**
写盘停顿期间定时器误点，是症状不是故障。只要没有 `sd cbuf full`，数据就没丢。

**Q9：屏上 `w:` 不涨？**
说明没有数据真正落盘。`w:` 每 2 秒刷新一次，只统计已提交到文件的字节数。
